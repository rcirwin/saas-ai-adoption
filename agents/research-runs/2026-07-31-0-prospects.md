### 2. WebFetch is globally blocked — third consecutive run

Per the 07-30 learning, a **cheap Wikipedia control fetch was run first** this time, before spending
any budget on prospect domains. It returned **HTTP 403**, confirming WebFetch is dead for *all* hosts,
not just prospect domains. The control-fetch-first tactic worked exactly as intended and cost one call.

`curl "$HTTPS_PROXY/__agentproxy/status"` reports the proxy `enabled: true` with an empty
`recentRelayFailures` list, i.e. the 403 is an **egress allow-list policy decision**, not a transport

routed around.

**No research depended on this during this run** (the queue was empty), so there is no data-quality
consequence today. But it will degrade the *next* real run, which would be the **fourth** consecutive
WebSearch-only run. Search snippets are summarised secondary content, and the 07-29 and 07-30 runs
already flagged that `none`/`exploring` postures derived from snippets alone are **provisional** —
a vendor's own site is where AI features get announced.

**Escalation**: ask the operator to restore WebFetch egress (at minimum prospect domains plus the
review/directory hosts G2, Capterra, SoftwareAdvice, SourceForge, Crunchbase) **before the
2026-08-04 batch lands.**

### 3. Agent-definition vs schema conflict (re-reported, 6th consecutive run)

Agent definition step 8 instructs writing `ai_posture` and `fit_score` into the `research_cache`
upsert, and step 5 instructs restoring both from a cache hit. The authoritative

`recommended_angle`** — neither column exists.

Reference wins, so both fields are written to the `prospects` tab only (columns L and M). The real

the agent definition rather than re-reported** — either drop the two fields from step 8, or add the two
columns to the `research_cache` tab and the schema doc.
